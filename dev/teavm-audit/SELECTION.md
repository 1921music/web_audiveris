# 解析対象の選別と除外対象への経路

取り込み分類をTeaVMの解析起点に反映し、不要クラス・不要メソッドを強制起点から外した。その後も再到達する経路を一覧化した。元アプリのソース、classの実装、依存先の実装は変更していない。互換実装、無処理の置換、移植実装は追加していない。

## 実行した範囲

`root-policy.json`でクラスとメソッドの選別規則を定義し、全14,390メソッドについて採否と理由を生成するようにした。

| 起点の扱い | メソッド数 | 意味 |
| --- | ---: | --- |
| `root` | 9,001 | 取り込み・一部取り込みクラス内の非UI候補。明示的に解析対象にする |
| `excluded` | 4,425 | 不要クラス、UI、学習、デバッグ、`.omr`保存、手動編集など。強制起点にしない |
| `dependency-only` | 964 | OCR・設定・実行器・フォントなどの境界と要確認メタデータ。必要側から参照された範囲で追跡する |

選択された起点の所有クラスは1,161個。本体を持つ8,588メソッドはすべて解析されたことを確認した。除外クラス・除外メソッドの強制起点への混入は0件で、Python側の選別とJava側の計画読込の両方で検査する。元クラスの増減と計画の不一致も検出する。

全元コードのJVMコンパイルは維持し、元のclassファイルをTeaVMのクラスパスに残している。除外クラスをjavacから取り除いたり、TeaVMのクラスフィルタで隠したりしていない。そのため、必要側から参照されれば再到達として観測できる。

これは最終的なエンジンAPIを決めたものではない。認識・データ処理の候補メソッドを広く起点にする調査プロファイルで、実際の処理入口を決めればさらに絞れる。

## 分類規則の補足

初回調査で必要側に残っていた次のものを、元コードの役割を確認して除外候補へ移した。

- `CheckBoard`、`CheckPanel`：UIコンポーネントを内包するチェック結果の表示用ラッパー。
- `sig.inter`内の`Editor`とその内包クラス：UI用の基底クラスを継承するが、パッケージ名だけでは判定できなかったもの。
- `SymbolSample`：フォントから学習用サンプルを作るクラス。
- UIラッパーの派生・内包クラスも、GUI用途を引き継ぐものとして判定する。

この補足後の全2,194クラスの分類は、取り込み1,069、一部取り込み96、境界179、除外848、要確認2。初回の比較用データは`results/`に保持し、今回の結果は`selected-results/`へ分離した。

メソッド単位では、描画・チャート・dump・main、分類器とニューラルネットワークの学習・モデル書出し、Book/Sheetの保存・画像ロード・GUI管理、手動編集の入口などを起点から外した。除外メソッド内のlambda補助メソッドも同じ規則で扱う。

推論の`run/forward`、モデルの`unmarshal`、認識用画像の生成、MusicXMLの`export`、認識に使う`searchLinks`は一括除外していない。`ui.symbol`の記号・フォント群も、一律に不要クラスとはしていない。規則ごとの理由と具体的な対象は[method-exclusions.tsv](selected-results/method-exclusions.tsv)に保存する。

選別後も、次の再到達が残っている。

| 検出したもの | 件数 |
| --- | ---: |
| 除外候補クラスへのリンク | 536クラス |

### 残っている主な入口

次の例は、TeaVMの型推定だけから作った推測ではなく、元アプリのメソッド本体にある参照とソース行を確認できるもの。

| 参照元 | 除外側への参照 | 次に切り分ける役割 |
| --- | --- | --- |
| `ConstantManager.addConstant`、187・190行 | `Main.getCli`、`CLI.getConstants` | 認識設定の供給とデスクトップCLIの接続 |
| `WellKnowns.<clinit>`、187行 | `LogUtil.initialize` | 環境初期化・ログ設定 |
| `Sheet.initTransients`、1225–1226行 | `OMR.gui`の型、`SelectionService`の生成 | 認識状態と画面通知・選択サービス |
| `FilamentIndex.<init>`、84–85行 | `OMR.gui`の型、`FilamentService`の生成 | インデックスとUIイベントの接続 |
| `AbstractWeightedEntity.addAttachment`、91–95行 | `AttachmentHolder` | デバッグ用図形の保持 |
| `BasicClassifier.<init>`、115・131・135行 | チャートリスナーの型、`createModel`、`NeuralNetwork.dump` | 推論モデル読込と初期モデル生成・デバッグ |
| `Book.export`、592行 | `OMR.gui`の型、`Main.getCli`、`CLI.isSwap` | MusicXML出力とCLI・ディスク退避の接続 |

`if (OMR.gui != null)`の中にある処理など、実際には実行しない可能性のある参照も含む。例えばCLIは今回、メソッド使用のない型情報だけの到達として記録されている。一方、`Main`の静的初期化は別途到達している。型依存と実行候補を一括で同じものとは扱っていない。

`Colors`の定数参照なども多いが、それだけでUI全体の取り込みが必要になるとは判断しない。小さな互換実装・通知先の分離で多数の参照を吸収できる可能性があり、今回の一覧はその判断材料になる。

## 出力と経路の意味

- [root-selection.json](selected-results/root-selection.json)：採否件数、規則・クラス分類・入力インベントリのハッシュ。
- [entry-boundaries.tsv](selected-results/entry-boundaries.tsv)：必要側・境界側から除外対象へ入る1,301件の参照。参照元、対象、命令種別、元ソース位置を保持する。
- [original-reference-paths.tsv](selected-results/original-reference-paths.tsv)：元アプリの宣言された呼び出しだけをつないだ参照経路。フィールド型・構築命令は呼び出しと区別する。
- [excluded-class-paths.tsv](selected-results/excluded-class-paths.tsv)：除外候補536クラスごとの代表的な最短経路、または型情報のみであることの表示。
- [diagnostics.tsv](selected-results/diagnostics.tsv)：選別後の全1,276診断。
- [classes.tsv](selected-results/classes.tsv)：補足後の全クラス分類。

全14,390メソッドの採否表、選択された9,001起点、全2,502除外メソッドの経路、使用判定、元メソッド本体の参照表、圧縮した呼び出しグラフは`wsl-artifacts/teavm-audit/fast-selected/`に保存する。

TeaVMの軽量解析は仮想呼び出しの型を広めに推定する。TeaVMの経路は実行ログではなく、解析上の到達候補である。元コード上の参照経路も条件分岐を評価した実行の証明ではない。各表では、元コードの参照位置を対応付けられた辺と、TeaVMの推定辺を区別する。

除外メソッドへの到達2,502件はすべて、選択起点からのTeaVM呼び出しグラフ上の経路を記録できた。型情報だけのクラスは実行経路を捏造せず、`type-only`と明示している。

## 再実行と検査

```powershell
.\dev\wsl\Manage-WasmDev.ps1 Build -GradleArgs @(
    'traceTeaVMExclusions', '-I', 'dev/teavm-audit/audit.init.gradle',
    '-PauditScope=selected', '--console=plain'
)
```

起点生成・クラス分類・TeaVM解析・診断集計・経路出力まで実行する。選別規則、推論と画像生成の保持、UIラッパーの派生判定、循環を持つ経路探索、除外ガードの8テストも実行して通過した。

`-PfailOnExcluded=true`を追加すると、除外対象への再到達が残っている場合は失敗させられる。現時点の厳密な除外判定は失敗になる想定で、検出した経路は出力後に残す。今回はその経路の調査までが対象であり、通知・初期化・入出力などの境界を置換していないためである。

CPU最大3論理CPU、作業全体のメモリ8 GiB、スワップ0を維持した。cgroupのローカルな上限到達・OOM・OOM killはいずれも0。元アプリと`buildSrc`の追跡ファイルが基準コミットから変わっていないことも確認した。
