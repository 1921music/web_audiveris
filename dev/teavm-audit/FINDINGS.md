# 元コードのTeaVMコンパイル調査

これは初回の全メソッド調査の記録。取り込み方針を解析起点へ反映した後の結果は[対象選別と除外経路の調査](SELECTION.md)を参照する。初回の結果表は比較用に保持している。

元コードの全メソッドをTeaVM 0.16.0のWasm GC向け解析に投入したところ、1,375件、重複するメッセージをまとめると351種類のエラーが出た。認識アルゴリズムを広く書き直す必要がある、という結果ではない。まず初期版に不要なUI・学習・デスクトップ機能を対象外にし、残る不足APIを互換層や境界の置換で吸収する検討が適切である。

クラスの取り込み判断は、GRAY8画像から認識・MusicXML出力まで、OCRは外部アダプタ、UI・学習・`.omr`保存は初期版の対象外、というこれまでの方針に基づく。

## 調査対象と解析の確認

- 元コードの基準コミット：`04697c74fae431ef8436a9429386957a5cb25993`。
- `app`と`buildSrc`の追跡ファイルは基準コミットから変更なし。調査用コードは`dev/teavm-audit`に分離した。
- 元アプリのJVMコンパイルは成功。生成されるビルド識別情報は通常のGradle処理で更新される。
- 元アプリのclassファイルは2,194個。入れ子・匿名クラスをまとめたトップレベルの型は939個。
- 宣言メソッド14,390個すべてを`linkMethod(...).use()`で明示的に解析対象にした。private・synthetic・コンストラクタ・クラス初期化子・abstract・nativeも対象。
- 本体を持つ13,857メソッドは、依存解析器の処理完了を全件確認した。残りはabstract・nativeなど本体のないメソッド。
- UI側のメソッドは3,720個、非UI側は10,670個。非UI側には起動・保存・学習補助も含むため、そのまま最終エンジンの入口集合とはしない。
- 使用メソッドを持つクラスは2,187個。残る7個は宣言メソッドを持たない型で、クラス一覧には含めた。

`classesToPreserve`だけで全メソッドが残るとは仮定していない。全メソッドを明示的に登録し、登録状況と本体の解析完了を`roots.tsv`に記録した。第三者ライブラリは、アプリのメソッドからTeaVMが追跡した範囲を対象とし、そのライブラリの全メソッドを別途強制登録したわけではない。

最終結果はTeaVM標準の軽量依存解析器によるもの。精密モードの全体解析は依存拡大のコストが大きいため途中で停止し、集計には使用していない。最終の軽量解析は約38秒で完了し、コンパイラ内部例外はなかった。軽量解析は型の流れを広めに見積もるため、実際の認識入口では不要な経路も含む。

CPUは共有cgroupで最大3論理CPU、メモリは作業全体で8 GiB、7 GiBから回収圧力、スワップ0。調査JVMのヒープは5 GiB。cgroupのローカルなOOM・OOM kill・上限到達カウンタはいずれも0だった。

## クラスの取り込み判断

全クラスの判断・理由・元ソースは[classes.tsv](results/classes.tsv)、件数は[class-summary.json](results/class-summary.json)に保存した。

| 判断 | classファイル数 | トップレベル型数 | 意味と代表例 |
| --- | ---: | ---: | --- |
| `keep` 取り込み | 1,136 | 504 | 認識・数値計算・データモデル。ラン・セクションの計算、スケール推定、特徴量、音符間の関係、リズム、MusicXML構築など |
| `mixed` 一部取り込み | 99 | 69 | 必要なクラスに不要な責務が混在。`Book`、`Sheet`、`SheetStub`、`Picture`、`BasicClassifier`、`BasicSection`など |
| `boundary` 境界として対応 | 183 | 79 | 必要な役割が環境依存。OCR実装、実行器、設定、リソース・ファイル・XML出力、記号・フォント群など |
| `exclude` 初期版では不要 | 774 | 285 | デスクトップUI、ダイアログ、ビュー、学習・サンプル管理、CLI・起動、開発ツール、画像/PDFデコード、外部アプリ連携など |
| `review` 要確認 | 2 | 2 | `ProgramId`と`sheet.package-info`。ビルド識別・XMLメタデータをどこまで利用するかで決める |

これは役割と対象範囲による分類で、ブラウザエンジンの最小依存集合が確定したという意味ではない。`keep`でも全メソッドが必要とは限らず、現時点でコンパイル可能という意味でもない。`exclude`も、参照が残った状態で単純にソースを削除してよいという意味ではない。

具体的には、次の区別が重要になる。

- `ui.symbol`の`MusicFont`、`OmrFont`、`TemplateSymbol`、`ShapeSymbol`などは、認識テンプレートや寸法計算から使われる。UIパッケージだからといって全削除せず、必要APIの取り込み・代替実装の候補とした。派生記号・フォントごとの必要性は、利用する認識入口・フォント設定でさらに絞れる。
- `Book`や`Sheet`は、認識データと保存・UI通知を同居させている。認識データまで作り直す判断にはせず、不要経路を解析対象から外すか、境界で吸収する候補とした。
- `BasicClassifier`や`NeuralNetwork`では推論が必要でも、学習・サンプル収集・チャート表示は不要。クラスを残したまま未使用メソッドを到達不能にできれば、全体を書き直す必要はない。
- `OmrShape`はデータセット用パッケージにあるが、認識処理が値を直接使うので残す。一方、データセット注釈の出力コンテナなどは対象外とした。
- `ImageLoading`とそのPDF/ImageIO依存は画像デコードを外側で行う方針により対象外。内部の画像加工・二値化・テンプレート照合まで外すわけではない。

取り込み・一部取り込みのクラスから、除外候補への参照が634本ある。[kept-to-excluded.tsv](results/kept-to-excluded.tsv)に全件保存した。フィールド・型シグネチャ・未使用メソッド・匿名クラスの参照も含むため、634箇所の手修正が必要という件数ではない。実際の入口からの到達性と、互換層・無処理の通知先などで吸収できる範囲を確認するための一覧である。

依存ライブラリ側の扱いも、役割で分けられる。

| 依存群 | 初期版での扱い |
| --- | --- |
| Swing、BSAF、JGoodies、チャートUI | UI機能として対象外。認識コードに残る通知・デバッグ呼び出しは別途切り分ける |
| PDFBox、JAI/ImageIOの画像デコード部分 | 外部でGRAY8化するため対象外 |
| GitHub API、Reflectionsの環境探索、任意のログバックエンド | 認識に必要な役割だけ残す。全ライブラリをそのまま持ち込む前提にしない |
| Tesseract／LeptonicaのJavaバインディング | Wasmエンジンへ直接取り込まず、既定方針の外部OCRアダプタの対象 |
| ImageJの画素処理、JGraphT、Jama、記号分類の数値計算 | 認識に必要な範囲を取り込み候補とする。ImageJのGUIやプラグイン全体は不要 |
| ProxyMusic／JAXB／ZIP | 楽譜データとMusicXML出力は必要。読込・保存・任意形式・圧縮の利用範囲を分ける |

## 出たエラー

全診断は[diagnostics.tsv](results/diagnostics.tsv)、重複集約は[apis.tsv](results/apis.tsv)、機械集計は[diagnostic-summary.json](results/diagnostic-summary.json)に保存した。

### 診断が直接発生した場所

| 場所 | 件数 |
| --- | ---: |
| 元アプリの非UIメソッド | 78 |
| 元アプリのUIメソッド | 84 |
| 依存ライブラリ・JDK内部 | 1,211 |
| 呼び出し位置を持たない継承関係のエラー | 2 |
| 合計 | 1,375 |

UIメソッドの判定はパッケージ名に加え、AWTコンポーネントの継承、Swing・Graphics・イベント型を持つシグネチャ、描画・チャート用メソッドも参照した。UI外パッケージの描画メソッドもUI側に入る。

クラスの取り込み判断で見ると、取り込み候補内で直接40件、一部取り込み内29件、境界内20件、除外候補内73件。取り込み候補のクラスにもデバッグ用メソッドなどがあるため、この40件がすべて認識実行時に必要な修正という意味ではない。

呼び出しグラフも追跡したが、全メソッドを起点にすると、UIのみから到達9件、非UIのみ17件、両方1,347件、未分類2件になった。非UIコードにもUI初期化・通知などが混在し、軽量解析の型推定も広いため、**「UI由来は9件だけ」と解釈してはいけない**。直接の発生位置・クラスの役割・具体的な呼び出しを併せて判断する。

### エンジン側で確認できた具体例

| 不足・問題 | 発生例 | 対応方針の候補 |
| --- | --- | --- |
| `Point.getX/getY`、コピーコンストラクタ、`translate`、`distanceSq`など | `Orientation`、曲線・ステム・音符データ、`OcrUtil` | AWT互換実装の補完。認識式やデータ構造の書き直しを先に行う根拠にはならない |
| `Color`の定数・`getRGB`・`decode` | `TemplateFactory`、`DistanceTable`、`Constant` | 必要機能の互換実装。デバッグ色と認識用画素生成は分ける |
| `Collections.unmodifiableSortedSet` | `SectionCompound.getMembers` | 小さな標準API互換。セクションを整数配列に全面変更する必要はない |
| `File.toPath`、ファイルチャネル・パスマッチ | 分類モデル読込、`FileUtil` | モデル・入出力の境界。ホスト側のバイト列・リソース提供と接続する候補 |
| `Properties.loadFromXML/store` | `Language`、`ConstantManager` | 固定リソースの事前変換や設定の差し替えを検討 |
| クラスローダー・ProtectionDomain | `WellKnowns` | インストール環境・リソース探索をブラウザ用設定へ置換する候補 |
| スレッドグループ・Threadコンストラクタ | `OmrExecutors` | 単一Worker内の実行制御へ置換する候補 |

TeaVM標準のAWT互換クラスはゼロではないが、0.16.0の`TPoint`は`x/y`と2整数のコンストラクタのみ、`TDimension`も同様の最小実装だった。`TColor`も限定的な定数・操作しか持たない。今回の`Point`・`Color`のエラーは、この不足と整合する。呼び出し側を維持したまま互換実装を提供する検討が先になる。

### ライブラリ側のエラーの読み方

例として、Windows LookAndFeel、Log4j、OkHttp、JBoss VFS、PDF暗号化、FastInfosetなどの任意経路に必要なクラスがない、という診断も出ている。未使用機能まで強制解析した影響を含むので、不足JARを全部追加するのが適切とは限らない。まず機能を対象外にするか、必要な実装だけ選ぶ。

また、反射APIがコンパイルエラーにならなかったことは、反射で必要なフィールドやコンストラクタが自動保持される証明にはならない。リソース読込や反射対象の設定は、入口を絞った後の確認が必要である。

## この段階で確定していないこと

依存解析でエラーが出たため、Wasmのコード生成段階には進んでいない。未検証のバックエンド制約やnativeメソッドが、その後に追加の診断を出す可能性はある。アプリ内のnativeメソッド5個は`WellKnowns`のGTK/GDK画面倍率取得で、認識本体として持ち込む役割ではない。

フォント計測・ラスタライズの一致、OCRの中断再開、実行時のリソース・メモリ、認識結果・速度・配布サイズもこの静的調査では未検証。エラーが出なかったクラスを、そのまま完全互換と判定していない。

今回は調査ツール・クラス分類・診断表までを作成した。元コードの削除、互換層の追加、クラス置換、移植実装はいずれも行っていない。

再実行方法は[README](README.md)、詳細な生データはリポジトリ直下の`wsl-artifacts/teavm-audit/fast-all`に保存する。呼び出しグラフは大きいため圧縮し、Gitには比較・レビュー用の表と要約を保存する。
